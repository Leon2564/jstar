## 0. 定位与运行模式

- **v1.0 正式**：与实体卡同日上线（10/30）。免费上线：不开任何购买（`RULES.shopOpen = false`，`/v1/shop/*` 一律 404 `shop_closed`）；点数只来自新人礼、每日登录与月度签到（§6）；月卡只来自幸运卡序列码（§5）。
- **v1.1「一起生活」**：v1.0 上线之后开工，不塞进 10/30。不做数字人实时层，不开真实付费（#47）。
- **演示模式**（`DEMO_MODE=true`：测试站 test.jstarcards.ai 与本地 `npm run demo`；生产禁止开启，API 检测到会拒绝启动）：邮箱验证码固定为 `123456` 并在界面提示；预置 5 个演示序列码；片段未到的场景与（若有）未审校的台词可用（§9.4）；各功能的 `/demo` 接口可用（`docs/api.md`）。
- 历史：2026-09-24 的「Demo 版」面向经纪公司与合作方演示（要求体验完整、不出现方括号占位，素材槽位保留规格说明）；v1.0 起面向真实用户。

## 1. 产品一句话

授权艺人（First Five：5 人 × 30 张 = 150 张 Star Genesis 数字卡，五档 N / R / SR / SSR / UR，全部 AI 生成，见 `docs/catalog-spec.md`）的数字卡牌收藏 + 本人公认 AI 陪伴聊天。实体盲盒卡附序列码，把线下用户导到线上。

## 2. 用户身份与年龄

| 规则 | 值 |
|---|---|
| 全站年龄确认 | 首次访问必须确认 18 岁以上，拒绝则无法进入 |
| 注册方式 | 仅邮箱验证码：同一流程既注册也登录（菜单「ログイン」/ `#/login` 打开登录文案）。LINE 登录已于 2026-09-27 按负责人决定移除，v1.0 不提供 |
| 注册后确认生年月日 | 注册后立即询问一次（`POST /v1/auth/me/birthday`），未满 `RULES.minAge`（18）当场关闭账号（按注销处理，403 `underage`）。生日只填一次（`docs/compliance-jp.md` §6） |

访客在未注册时拥有一个**设备身份**（浏览器生成的 device id）。访客试聊记录、访客兑换的卡都挂在设备身份上，注册（或登录）时整体转入账号，这一步叫**认领**。

## 3. 聊天

### 3.1 次数规则

| 身份 | 额度 | 用完之后 |
|---|---|---|
| 访客 | 每台设备共 **3 条**（`RULES.trialMessages`，不按天重置） | 引导注册，注册后对话继续 |
| 注册用户 | 每天 **20 条**免费（`RULES.dailyFreeMessages`），所有艺人合计，**日本时间 0:00** 重置（待确认） | 提示月卡，或次日再来 |
| 月卡有效期内 | 不限条数（合理使用上限每天 **300 条**，`RULES.passFairUseMessages`，防刷，不在界面展示） | — |

- 次数只由服务端判定，前端显示的剩余条数只是回显。
- 被内容边界硬拦截的消息**不扣次数**；人设婉拒的消息正常扣次数。

### 3.2 亲密度与回忆卡

- 每条消息 +8 亲密度（`RULES.xpPerMessage`，按艺人分开计算），每 40 升一级（`RULES.xpPerLevel`，等级只作展示）。免费单抽改为**每进入一个关系阶段 / 恋人每升一级送 1 次**（v1.1，§10.1），不再每级送。
- 与同一位艺人每聊满 3 条（`RULES.memoryCardEvery`），生成一张回忆卡。标题由模型概括成一句（与回复并行生成：记忆更新到期的轮次由记忆模型写，其余轮次由一次只写标题的小调用写，规则相同），**不截取用户原话**；婉拒、自伤等轮次不生成。
- 长期记忆分批更新（2026-09-29 降本）：他与同一位艺人第 5 条还没进记忆的消息时，记忆模型一次读完这几轮；出现约定线索（明日 / 9時 / 約束 / tomorrow 等时间词）或她的样子可夸时他夸了她，当轮就更新。其间的轮次存在服务端（`chat_memory.pending`），她回复时照样看得到（都在最近 12 条的上下文里）；他离开聊天页、或 10 分钟没有新消息时一并记下。什么都不丢：记忆模型失败时这些轮次留着下次再试。
- 卡片详情里的「ストーリー第2話」在与该艺人的关系进入「仲良し」（familiar，`STAGE_RULES.storyTwoStage`）时解锁（v1.1 起；原为亲密度 Lv.3，同为 80 亲密度）。
- 回忆卡的类型、导出与删除见 §15。

## 5. 序列码（实体幸运卡 → 线上）

流程：**先兑换，后注册认领**。码由 `tools/luckcards` 生成并交印厂（2026A 38,400 张、2026B 10,000 张），库里只存哈希。

1. 扫卡背二维码：通用码 `https://jstarcards.ai/lucky` 打开兑换页；逐张码 `https://jstarcards.ai/r/<12位码>` 打开兑换页并自动填码。两者都先经过年龄确认，码保留。也可手动输入。
2. 兑换成功 → 6 张卡背朝上发牌 → 逐张或一次翻开 → 她说一句话 → 显示特典「マンスリーパス7日間」。
3. 访客：卡和体验天数挂在设备上，页面引导「无料登録してカードを保存する」；注册后自动认领（卡、重复卡的羁绊、天数、兑换记录一并转入）。已登录用户直接入账。
4. 一码一用：同一个码第二次兑换返回「已使用」，不论是不是同一个人；并发同时提交只有一个成功。兑换（标记已用 + 发卡 + 天数 + 抽卡记录）在一个事务里完成，中途失败不会白白消耗码。
5. 防爆破：同一设备连续 5 次「码不存在」（`RULES.serialMaxFailures`）锁定 10 分钟（`RULES.serialLockMs`）；同一 IP 放宽到 4 倍即 20 次（`apps/api/src/modules/serial.ts` 的 `IP_FAILURE_FACTOR`；活动现场、店铺 Wi-Fi 会共用一个 IP）。校验位不对的输入是打错字，前端直接提示，服务端也不计入失败。服务端判定。

| 项 | 值 |
|---|---|
| 码格式 | 12 位数字，首位 1–9，末位 Luhn 校验位；印刷为 `1234-5678-9012`。输入时空格、横线、全角数字都可以 |
| 存储 | `HMAC-SHA256(密钥, 码)`，密钥即 `tools/luckcards/out/code-hmac.secret`（线上为 Worker secret `SERIAL_HMAC_KEY`）。**密钥丢失 = 全部已印码作废** |
| 一个码给什么 | **6 抽**（`RULES.lucky.drawsPerCode`）+ **7 天月卡体验**（`RULES.serialDefaultTrialDays`，待确认），第 1 抽保底 SR 以上（按批次配置） |
| 概率 | 从全部 150 张抽（卡池 `lucky-s1`），档位概率与付费抽卡相同：N 55% / R 28% / SR 12% / SSR 4.5% / UR 0.5%（`RULES.lucky.tierRates`）。第 1 张只在 SR 以上按同比例归一：SR 70.6% / SSR 26.5% / UR 2.9% |
| 重复卡 | 张数 +1（用于覚醒），并给该艺人 +20 亲密度（`RULES.lucky.duplicateBondXp`，羁绊；不发升级免费抽） |
| 抽卡记录 | 每次兑换保存随机种子、五档档位和结果，可复现 |
| 演示码 | `DEMO_MODE` 预置 5 个（`9990-0000-0011` 等），同样一码一用；迁移 `0005_end_demo.sql` 会把它们标为已用。后台可另行生成小批量码（活动、合作方样卡） |
| 访客兑换后一直不注册 | 卡留在该设备上；清除浏览器数据即丢失（**待确认**：是否提供找回途径） |

## 7. 内容边界（不变）

性感不露骨。露骨请求由人设婉拒；未成年、非自愿、索要现实住址、跟踪直接拦截；自伤倾向给出求助信息；问「是不是真人」必须说明是 AI。规则只在 `apps/agent` 里定义。v1.1 的场景同样只到近景、耳边说话、拥抱，越线由她用人设拒绝，不弹系统提示。

## 8. 范围：v1.0 与 v1.1

**v1.0 做**：用户端全部走 API（试聊、注册认领、聊天次数、亲密度、回忆卡、抽卡含免费抽与天井、碎片兑换、序列码、每日登录与签到）；刷新后以服务端为准；所有请求失败有明确提示；API 在生产环境检测到默认密钥或演示模式时拒绝启动；扣点数、扣免费次数都是带条件的原子操作。

**v1.1 做**（#47）：§9–§16。约会与相处（场景、约定）、换装（变体卡）、小游戏（场景内的猜拳、大喜利等）、语音输入，都是 v1.0 不做、v1.1 做。

**两期都不做**：真实支付（点数与月卡只来自免费渠道）、数字人实时层（等合作方）、真实 LINE OAuth、Redis（序列码锁定仍在进程内，见 `docs/security.md`）、集齐换奖（`docs/compliance-jp.md` §2）。

## 9. v1.1 基础

### 9.1 艺人档案与世界配置（#48）

- 单一出处 `packages/shared/src/world.ts`：五位的生日（MM-DD，不含年份）、家乡（只到城市级别）、作息（§11.1）、招牌场景、称呼模板（§10.3）、季节（§11.5）。web、API、admin 与 persona 服务都从这里读。
- 生日与家乡是真人的事实：`{ value, confirmed }`。**负责人 2026-09-28 已确认五位**（まひろ 03-04 东京、奈々 09-03 长野、うんぱい 07-17 仙台、アリス 02-25 埼玉、えいみ 03-18 栃木），全部 `confirmed: true`：她的生日进日历，天气按她的城市，城市名可以出现在首页与提示词里。规则不变：只读 `confirmedWorld()`，以后新增的值先 `confirmed: false`，未确认时任何页面、提示词、消息里都不出现、天气退回东京（`weatherPoint()`）；确认后在 PR 里改为 true，再跑 `npm run world:agent -w @jstar/shared` 生成 `apps/agent/app/world.json`（CI 比对）。演示模式例外：未确认的生日也当作已确认（§11.5）。
- 管理后台「Talent world」只读页显示每位的确认状态。

### 9.2 定时任务与收件箱（#49）

- Cron Trigger 每 5 分钟（`wrangler*.jsonc` 的 `triggers.crons`）调用 API 的 `POST /v1/ops/tick`；公网访问 `/v1/ops/*` 一律 404。她主动的一切（约定到期、叫醒、天气、节点、告白邀请、她的消息、回忆资产、天气刷新）都是 tick 里的任务，顺序与规则见 `docs/architecture.md`「定时任务」。
- 收件箱（D1 `inbox`）：任务提前写好 `due_at`，tick 到点投递（`delivered_at`），同一行只投递一次；只显示已投递的，未读优先、最近 50 条。陪伴首页她的头像上是未读角标（`/v1/auth/me` 的 `inboxUnread`）；点开 = 进入她的聊天，这条是她的开场并标为已读。
- 退会时删除全部收件。

### 9.3 推送与 PWA（#50）

- 网站可安装（manifest）；Service Worker 只处理推送与点击，不做任何缓存。iOS 只有「添加到主屏幕」后才能收推送，未安装时「マイ」里显示三步引导。
- 只有用户在「マイ → 通知」主动开启后才请求权限；订阅时上报的浏览器时区写入 `users.tz`（叫醒、她的消息按它计时）。
- 锁屏上只有她的名字和她的一句话，不含聊天原文或个人信息；点击直达对应画面。
- 没配 VAPID 密钥时推送整体关闭，界面不出现开关，其他功能照常。退出登录、退会时先删除这台浏览器的订阅。

### 9.4 审校、发布与演示模式

**台词**：v1.1 的台词（#82，`packages/shared/src/lines/*.json`、场景脚本、`CALENDAR_LINES` / `HER_MESSAGE_LINES` / `PROMISE_LINES` / `GIFT_REACTIONS`）已于 2026-09-28 由 OpenRouter 上的 SOTA 模型做完母语审校（#84，负责人决定；记录见 `docs/review/v11-lines-review.md`），各台词集 `draft: false`，正式环境照常使用：告白（§10.2）、称呼的提问（§10.3）、叫醒话（§11.2）、约定（§11.4）、天气消息（§12.2）、系统场景（§13.3）、Pickup 的主动邀约（§14.2）、变体卡当晚的邀约（§14.1）。以后某个台词集改回 `draft: true`，它就只在演示模式出现（上述各功能的门槛代码保留）。

## 10. 关系阶段

### 10.1 阶段与相处天数（#54）

- 每位艺人一条独立的关系线：**出会ったばかり（new）→ 仲良し（familiar）→ 気になるふたり（ambiguous）→ 告白（confession_ready，§10.2）→ 恋人（lover）**。和一位聊天或看场景，不改变其他四位。
- **相处天数** = 与她有过至少 1 条消息或 1 次场景的 JST 日期数（不是注册后的自然日）；每天第一次互动 +1。
- 进入下一阶段要同时满足：在当前阶段相处满**最少天数**，且亲密度（累计值，即原来的 `affinity.xp`）达标。亲密度再多也跳不过天数，所以告白最早在**第 7 个相处日**。

| 阶段 | 最少天数（`STAGE_RULES.stages.*.minDays`） | 亲密度门槛（`STAGE_RULES.stages.*.xp`） | 满足后 |
|---|---|---|---|
| new | 2 | 80 | → familiar |
| familiar | 2 | 200 | → ambiguous |
| ambiguous | 3 | 400 | → confession_ready（她在自己的场景里告白，§10.2） |

- 恋人等级 1–10（`STAGE_RULES.loverMaxLevel`）：从告白被接受时的亲密度起，每 300（`STAGE_RULES.loverXpPerLevel`）为一级。v1.1 的内容只写到 3 级（`STAGE_RULES.loverContentLevel`），更高只显示数字。
- 免费单抽：进入 familiar、ambiguous、lover 各 1 次，恋人每升一级 1 次，每位最多 12 次。confession_ready 对用户仍显示为 ambiguous，不另送。并发请求、重试都不会重复发（`reward_rank` 条件写入）。
- 首页关系面板：阶段名（三语）、相处天数、纪念日，和她的一句提示（「もう少し一緒に過ごしたら…」）——**只用她的话，不显示门槛数字**。
- 事件：阶段变化写 `stage.changed`（from / to）。
- 场景脚本可用 `trigger.stage` 限定最低阶段（`new` / `familiar` / `ambiguous` / `confession_ready` / `lover`），按真实阶段判定。
- 数值全部**待确认**（#84），在 `packages/shared/src/rules.ts` 的 `STAGE_RULES`，改数字不用改代码。
- **老用户迁移**（D1 `0007_relationship.sql`）：按原亲密度等级折算——Lv.1–2（< 80）→ new，Lv.3–5（80–199）→ familiar，Lv.6 以上（≥ 200）→ ambiguous；不会直接进 confession_ready / lover（那是事件）。相处天数按其历史消息的 JST 日期数重建。已开放的第 2 话、人设段落都不倒退；迁入的阶段视为已发过免费抽（按等级已发），之后只有进入更高阶段才再发。迁入 familiar / ambiguous 的用户从迁移时起重新计该阶段的天数。

### 10.2 告白（#55）

- 关系进入 `confession_ready`（最早第 7 个相处日）的那天，她先发一条消息（tick 的 `confession.invite`，在 `inbox.deliver` 之前，每轮一次），点开就进入告白。
- **JST 17:00 之后**（`CONFESSION_RULES.slots` = evening、night）第一次进她的房间，场景引擎直接播放 `confession-<star>`：全景开场 → 近景告白（字幕；预生成语音待 #83）→ 她问「恋人になってくれる？」。白天进房间她只暗示（首页问候换成她的 `hint` 台词）。当晚离开后再进房间不再自动打开，首页有「〇〇の話を聞く」入口。
- 他用语音回答（§13.4，按住说话），也可以打字；麦克风被拒时文字照常。回答由 persona 服务判定（`POST /v1/confession/judge`，先过与聊天相同的内容边界）：**accept / not_yet / decline**。模型不可用、输出不合法、信心不足、或他的话里有明确的「不 / 还没」时一律按 not_yet——错判成 yes 会直接成为恋人，错判成 not_yet 只是她过几天再问。
- **accept**：`stage = lover`，**纪念日 = 当天 JST 日期**，恋人阶段的免费单抽照 §10.1 发放；回忆卡「告白」+ 亲密度 +20（`CONFESSION_RULES.acceptAffinity`）；她第一次直呼他的名字（台词里的 `{name}`，§10.3）。他的回答文字与回忆卡一起保存；录音**只在他勾选「この答えの声を、思い出として残す」后**上传保存（`docs/compliance-jp.md` §7.3），在「思い出」页可回放、可单独删除。
- **not_yet / decline**：她不生气（各自的台词），当天不再触发；**再相处 2 天**（`CONFESSION_RULES.retryDays`）后重新发消息、换成 `confession-<star>-again`（以她的 `retry` 台词开场）。**第三次**（`CONFESSION_RULES.maxAsks`）不是 yes 之后她不再主动告白，关系仍停在（对他显示为）「気になるふたり」，首页出现「自分から想いを伝える」由他自己开启。沉默（5 分钟未回答）不算回答。
- 事件：开始时 `confession.reached`（每轮一次，admin「指標」的告白到达率），回答后 `confession.answered(answer)`；她发起的场景记为 `scene.trigger(source=proposed)`。
- 台词已审校（#84，§9.4），正式环境照常发消息、开放场景；台词集改回 `draft` 时只在演示模式出现。演示模式下告白不限 17:00 之后，便于白天验收。
- 数值（2 天、3 次、+20、录音上限 768 KB `CONFESSION_RULES.voiceMaxBytes`）在 `packages/shared/src/rules.ts` 的 `CONFESSION_RULES`，全部**待确认**。

### 10.3 称呼与「她会被你改变」（#56）

- **称呼按阶段**：每位的称呼模板在 `packages/shared/src/world.ts` 的 `callNames`（new / familiar / lover；ambiguous 与 confession_ready 沿用 familiar）。例：まひろ「{name}さん」→「{name}くん」→「{name}」；えいみ 从「{name}くん」开始，恋人阶段是「キミ」。随人设终稿确定（2026-09-28）。
- **{name}**：他在「我的 → 呼び方」设的名字（20 字内，`BOND_RULES.nameMax`；不含联系方式 / 链接 / 3 位以上数字，persona 服务再过一遍安全过滤，不通过就不进提示词）→ 他在聊天里告诉她的称呼 / 名字（记忆 facts）→ 账号昵称。名字本身已带敬称（ケンちゃん）时不再加さん / くん。
- **转换只问一次**：关系进入新的称呼阶段后，他下一次打开她的聊天，她先问（#82 `callName` 台词，「いいよ / いまのままで」两个按钮）。答应 → 从此用新称呼；不答应 → 保持旧称呼，这一步不再问。答案条件写入（两个标签页同时回答只记一次），写 events `call_name.answered(to, answer)`；她的提问与回答作为两条 assistant 消息进入对话历史（不扣次数、不算相处日）。跳过的阶段只问当前阶段（例如演示直接到 lover）。
- **提示词**：API 每轮把当前称呼（`callName`）交给 persona 服务，问候、聊天、她的消息都用同一个；提示词要求「始终用这个称呼，不自行改用别的名字或敬称」。
- 台词已审校（#84，§9.4），正式环境照常提问；台词集改回 `draft` 时正式环境不问，保持他上次答应的称呼（默认 new 阶段的称呼）。演示中把阶段调回更低时，高于该阶段的提问会被忘记，可以再试。
- **她会被你改变**：记忆模型（与记忆更新同一次调用，无模型时按关键词；他说了夸奖的话、且有可夸的样子时当轮更新记忆）判断他在最新一条消息里夸了她的哪种样子：`outfit`（她的常穿衣服，即房间视频里那一身）、`face`（笑容、眼睛、头发）、他拥有的她的变体卡（§14.1）。只存「哪种样子被夸了几次」，不存他的原话。夸满 **3 次**（`BOND_RULES.praisedAt`）→ 提示词里她知道「你喜欢这个，所以我更常给你看」；房间待机按权重抽：常穿 1、变体（有卡且有 `<star>-variant-home` 视频时）1，随变体等级上升，10 级可固定（§14.1）、近景（夸过脸之后才加入，竖屏）1，被夸满 3 次的 ×2（`BOND_RULES.praisedWeight`）。只在已存在的视频之间选择，不生成新素材。
- 退会时删除称呼状态、夸奖计数与「呼び方」。数值在 `rules.ts` 的 `BOND_RULES`，全部**待确认**。
- **他喜欢的相处方式**（`favorite_ways`）：记忆模型（与记忆更新同一次调用）归纳他明显喜欢的和她相处的方式，存进聊天记忆 facts：最多 5 个短标签（例「寝る前のおしゃべり」「朗読を聞くこと」），每个 24 字内、合计 80 字内；不存他的原话（带引号、句末标点、「俺は / 私の / I / my」的丢弃，与他这条消息逐字相同的长标签丢弃），不含联系方式、露骨或未成年相关词。无模型时按关键词记为固定标签（late-night talks 等），同样不留原话。提示词单列「他喜欢和你做的事」：自然地更常提议、他开头时顺势投入，不宣称「我记得」，也不每条都提。随退会删除（chat_memory）。
- **轻度吃醋**（`mentions_other`）：他的消息里出现其他四位的名字（五人的全名 / 名字，各语言写法；拉丁字母按整词，`banana` 不算 Nana）时，persona 服务给这一轮加一句提示：按她的 `jealousy` 人设轻度吃醋一句，力度随阶段（new 只轻轻嘟嘴 → lover 可以直说有点吃醋），然后回到两个人；不说对方坏话、不做对立或三角剧情、不编造对方或本人的事；他问起对方时温和地说更想听他的事。安全层的引导（露骨、见面、自伤等）优先，此时不加吃醋。评测集 `apps/agent/evals/jealousy_cases.yaml`（まひろ × 奈々 10 条，`python -m evals.jealousy`，付费，花费记 SPEND）。
- **禁聊清单**（`taboo:`）：每份 persona yaml 有 `taboo` 列表（字符串，或 `{topic, words}`）。**负责人 2026-09-28 决定不设禁聊清单**，五份都是 `taboo: []`。机制保留：非空时提示词边界里写「这些话题你从不主动提，被问到时礼貌带过、不解释、不谈内容」；他的消息命中某个话题的词时，这一轮再加一句带过的提示（优先于吃醋）；无模型时回她的 `deflection` 台词。五份人设已按公开资料与现有文件定稿（`draft: false`，2026-09-28）。

## 11. 一天的循环

### 11.1 五人作息与「现在谁在家」（#60）

- 作息只从 `world.ts` 读：每位四个时段（JST 早上 05–11 / 白天 11–17 / 晚上 17–23 / 深夜 23–05），每段是在家 / 外出 / 睡觉（`presence`）+ 三语状态短语 + 可选的活动 id（`activity`，如うんぱい 的 `walk-stream`）；任何时段至少一位在家（`worldProblems` 校验）。`routineNow()` 按 JST 计算，与访客或服务器的时区无关。
- 首页头像行：每位此刻在家 / 外出 / 睡觉与她城市的天气；名字下一行是她此刻在做什么 + 「日本 HH:MM · あなたの時間 HH:MM」（同时区只显示日本时间）。城市名只在家乡确认后显示（§9.1；五位都已确认）。
- 睡觉的她：头像变暗但可点；进房间是她被叫醒的台词（每位 3 句 `woken`，按日轮换），不调模型、不缓存，仍然可以聊，语气困、软、开心、不生气，不涉及任何性内容。
- 此刻的状态（presence + status）随每轮聊天与问候交给 persona 服务；问候缓存按时段区分；场景脚本的 `trigger.routine` 按它判定（例：うんぱい「あなただけの配信」只在她夜散步直播的 17–23 点可提议）。

### 11.2 叫醒闹钟（#57）

- 每位用户 **1 个**闹钟：时间（`HH:MM`，用户自己的时钟）、星期、由哪一位叫醒、开 / 关；在「我的」与陪伴首页的「目覚まし」进入设定（D1 `alarms`，迁移 0014）。门槛：`rules.ts` 的 `ACCESS.wakeup`，v1.1 为 `free`（将来放进月卡只改这一处）。
- 时区：按用户的时钟（`users.tz`：开通知或保存闹钟时由浏览器上报的 IANA 时区；没有则用保存闹钟时的时区，再没有按 JST，`WAKEUP_RULES.defaultTz`）。按时区的「墙上时间」判断，夏令时跳过的时刻在跳过后的第一次 tick 响，重复的一小时只响第一次。
- 触发：5 分钟 tick 的 `alarm.ring` 任务（排在 `inbox.deliver` 之前）写一条当下到期的 `wakeup` 收件，同一次 tick 投递并推送 → 设定时刻后 **5 分钟内**到达。每个本地日最多响 **1 次**（条件写 `alarms.last_day`，重复或并发的 tick 不会重复叫醒）；tick 迟到超过 **30 分钟**（`WAKEUP_RULES.ringWindowMs`，停机）则放弃当天，不在 10 点补叫 7:30 的闹钟。保存时当天时刻已过 → 从明天起；改成当天更晚的时刻 → 当天再响。
- 推送：标题 = 她的名字，正文 = 她的一句叫醒话，点击直达叫醒画面；TTL **30 分钟**（`WAKEUP_RULES.pushTtlSeconds`）、高优先级；「あと5分」的再叫用同一 tag 替换上一条。
- 叫醒话：#82 每位 8 句，按星期（平日 / 周末）与天气（他设了城市用他的城市，否则她的城市；雨 / 雪优先）轮换。台词已审校（§9.4），正式环境照常使用；台词集改回 `draft` 时，正式环境改用已录音的早安问候（`tools/voice/greetings.json` 的 morning），两个按钮不带她的回话。称呼：v1.1 的叫醒话不带称呼，全部可一次录音（#83）；需要带称呼时走运行时 TTS（#73），不做录音片段拼接。
- 叫醒画面（`/me/wake`）：她房间的早晨空镜 → 她（有 `<star>-hero-morning` 用它，否则 hero 片段加早晨光）；她的早安录音 + 当天的叫醒话 +「起きた？」：「起きた」/「あと5分」。「あと5分」**5 分钟**（`WAKEUP_RULES.snoozeMinutes`）后再叫一次，**每个早晨 1 次**（`WAKEUP_RULES.maxSnoozes`），只限当天。打开即算已读，写 events `wakeup.opened`（每个早晨一次）；保存（开启状态）写 `alarm.set`。
- 没开通知的用户：**11:00 前**（`WAKEUP_RULES.sceneUntilHour`，他的时钟）打开陪伴首页，当天未打开的叫醒会直接播放；之后在她头像的未读角标里，点开同样进入叫醒画面。
- 退会时删除闹钟。数值在 `rules.ts` 的 `WAKEUP_RULES`。合规见 `docs/compliance-jp.md` §7.2。

### 11.3 她的消息（#58）

- 谁会收到：近 7 个 JST 日（`HER_MESSAGE_RULES.activeDays`）内和她有过消息或场景的用户（`relationship.last_day`），未封禁、未退会、设置不是「受け取らない」。
- 一天的计划：在用户自己的时区（`users.tz`，未上报或无效 = JST）当天 05:00 之后决定一次：前一晚（前一天 18:00 至当天 05:00，`HER_MESSAGE_RULES.lastNight`）有互动 → 早上的「夢に出てきた」（对象是前一晚互动的那位）；然后今晚的邀约；然后日常动态——按设置取前几条（ふつう 2 / 少なめ 1 / 受け取らない 0）。时段（用户本地时间，`HER_MESSAGE_RULES.windows`）：梦 07–11、日常 11–16、邀约 16–20，每位用户在时段内有自己的时刻（分散推送）；22:00–07:00 静默（`HER_MESSAGE_RULES.quietHours`），任何消息都不发。
- 由谁来写：他最近一起度过的那位（`last_day` 最新，其次相处天数）；梦是前一晚那位。
- 生成：人设服务 `POST /v1/her-message`，记忆模型（`HER_MESSAGE_MODEL`，默认 gemini-3.1-flash-lite），带长期记忆（facts / summary）、关系阶段、她此刻的作息、她所在城市当天的天气（只给天气，不给城市名）、邀约时她的招牌场景；长度严格（ja 70 / zh-Hant 60 / en 160 / ko 80 字，`HER_MESSAGE_RULES.maxChars`，按句末截断，截不了就不用）。每条消息**最多调用一次模型**（不重试、不换备用模型）；安全过滤走正则层（露骨、未成年、非自愿、现实见面 / 联系方式、链接、号码、账号）；失败、超时或被过滤 → 她的预设台词（`HER_MESSAGE_LINES`，四语，已审校 #84）。
- 投递：inbox `message`（payload `{ text, herMessage, sceneId? }`），推送与角标在同一次 tick；打开 = 进入她的聊天，这条是她的开场，并作为一条 assistant 消息写入对话历史（不扣次数、不算相处日）；用户回复走正常聊天。邀约带上她今晚的场景（`sceneId`，仅限当前模式可开始、适合夜晚的场景）：打开时由场景触发（§13.2，`POST /v1/scene/room` 的 inbox 事件）提议进入——满足场景时段条件时是一个按钮，从不强制；不满足（白天）就先聊天。
- 上限（待确认，#84）：`HER_MESSAGE_RULES.perDay = 2`（herMessagesPerDay，「少なめ」为 `lessPerDay = 1`）、`dailyCap = 10,000` 条 / JST 日（herMessagesDailyCap），到达全局上限后当天只发给月卡用户。
- 幂等：`her_messages` 主键（用户, 本地日, kind）；planned → writing → sent / skipped，每一步都是单条条件语句，发送与 inbox 行同一事务；取走后未写完的行 10 分钟后用预设台词发出、不再调用模型；时段结束 30 分钟后仍未发出的丢弃（tick 停机时不会半夜补发）。
- 设置：「我的」→「彼女からのメッセージ」三档，立即生效；推送开关仍是各浏览器自己的。退会时删除该用户的计划行与设置。数值在 `rules.ts` 的 `HER_MESSAGE_RULES`。

### 11.4 约定（#59）

- 每位艺人同时最多 **1 条**未完成（`open`）约定；第二条在第一条兑现或错过前不会创建（D1 部分唯一索引 `idx_promises_open`）。
- 来源：①聊天里双方明确约好（他的消息里有时间线索时当轮更新记忆，记忆模型输出 `promise { text, due（绝对 JST 时间）, kind }`，API 再校验：10 分钟后至 14 天内，`PROMISE_RULES.chatMinAheadMs` / `chatMaxAheadMs`）；②她的提议（#82 台词，每位 5 句，按 JST 日轮换）——聊过之后离开房间前、或聊天 10 分钟（`PROMISE_RULES.idleProposeMs`）无消息时她提一句，用户点「約束する」才成立；③场景结尾步 `effect.promise`（与场景奖励同一事务写入，`sceneId` 记来源场景）。约定文字最长 60 字（`PROMISE_RULES.textMax`）。
- 写入记忆：未完成的约定（及刚兑现的约定）每轮都交给人设服务，出现在她的提示词里；有未完成约定时记忆模型不会再生成新的。
- 兑现：tick（`promises.due`，排在 `inbox.deliver` 之前）到 `due_at` 写 inbox `promise_due`（「昨日の約束、覚えてる？」），同一次 tick 推送并出角标，幂等。用户在 **due ± 3 小时**（`PROMISE_RULES.windowMs`）内打开这条消息或进入她的房间 → 她的开场就是兑现（替代当天问候，不缓存）→ `kept`，写 events `promise.kept`，并生成一张同名回忆卡。`kind = scene` 的约定在兑现窗口内进房间还会提供「約束の時間」场景（§13.3）。
- 错过：超过 due + 3 小时 → `missed`，未读的那条消息标为已读；下次进入她的房间她轻轻提一句（不责怪），只提一次。
- 指标：约定回访率 = kept /（kept + missed），events `promise.due` / `promise.kept` 按 `promiseId` 配对；在 tick 之前就兑现的约定也补记 `promise.due`。
- 她的提议台词与兑现 / 错过台词已审校（#84，§9.4），正式环境照常提议。
- 退会时删除该用户的全部约定。数值在 `packages/shared/src/rules.ts` 的 `PROMISE_RULES`。

## 12. 家乡与天气

### 12.1 气象数据（#62）

- 数据源 Open-Meteo（无密钥；日本境内默认融合气象厅 MSM）。天气点：她的城市（`weatherPoint()`，五位家乡已确认；未确认的家乡退回东京，§9.1）与用户自选城市的 0.1° 方格。
- tick 的 `weather.refresh` 约每小时刷新到期的点（`WEATHER_REFRESH_MS`，`packages/shared/src/weather.ts`）：当前天气、气温、今明两天的日出日落、未来 6 小时。失败不清数据，只记错误，15 分钟后重试（`WEATHER_RETRY_MS`）；超过 3 小时未更新（`WEATHER_STALE_MS`）标记 `stale`，读取方一律视为没有天气（首页不显示、提示词不传）。
- 预警按气象厅的描述性标准近似（`WEATHER_THRESHOLDS`）：强い雨 ≥ 20 mm/h、強い風 ≥ 15 m/s、暴风雨 = 风 ≥ 20 m/s 且雨 ≥ 10 mm/h、大雪 = 未来 6 小时累计 ≥ 5 cm、猛暑 ≥ 35 °C（均在当前与未来 6 小时内取最大）。初雪按寒候年（8 月–次年 7 月）每个点只记一次。
- 他的城市（可选，「マイ → あなたの街」）：按名称搜索城市级地点，服务端按 id 重新查询后只保存地名与取整到 0.1° 的坐标，不读浏览器定位；只用于天气；可随时清除，退会时删除（`docs/compliance-jp.md` §7.1）。
- 显示天气处都标注 Open-Meteo（CC BY 4.0）。免费档仅限非商业用途，正式商用需改用其付费档（#84）。

### 12.2 天气进入她的世界（#63）

- 房间：陪伴首页按她城市的真实日出日落调色，雨 / 暴风雨 / 雪 / 樱花季 / 午后酷热（≥ 32 °C，`WEATHER_EVENT_RULES.hotC`）是 CSS 图层；reduced-motion 下只保留调色与静止元素。雨声只在声音开启时播放。
- 对话：API 用自己存的天气组装 `world` 随聊天、场景内自由对话与问候交给 persona 服务，从不信任浏览器。家乡确认后才传城市名（五位都已确认），未确认时她只说「这里」；他设了城市且两地天气不同时，她在前几轮里轻轻对比一次。问候缓存按天气区分，下雨后再进房间第一句会提到雨。
- 场景：脚本的 `trigger.weather` 按她城市的真实天空判定，天气未知或过期视为不满足。
- 天气消息（tick 的 `weather.events`，读上一次刷新存下的天气）：初雪（每个寒候年一次）、台风 / 强风 / 大雨预警（她担心他）、雨夜（入夜后下雨，同一位每 3 天最多一次，`WEATHER_EVENT_RULES.rainyNightEveryDays`）。只发给 7 天内进过她房间的用户（`WEATHER_EVENT_RULES.activeDays`，`room.entered`），当地 7–23 点（`WEATHER_EVENT_RULES.hours`），每位每天至多一条、每个用户 24 小时内至多两条（`WEATHER_EVENT_RULES.perUserPerDay`）。消息带 `sceneId`，打开后提供对应的天气场景（§13.3）。台词已审校（§9.4），正式环境照常发。
- 测试站：`PUT /v1/world/demo` 把她城市的天气临时改成指定天空 / 预警 / 初雪，直到下一次整点刷新；首页 `?wx=rain|snow|storm|sakura|hot` 只画图层。

## 13. 场景与语音

### 13.1 场景引擎（#64）

- 脚本：`packages/shared/src/scenes/<star>/<id>.json`，zod 校验（`scenes/schema.ts`）；日文为准，繁中 / 英为字幕。尺度同 §7：最多到近景、耳边说话、拥抱。
- 一次运行最长 **30 分钟**（`SCENE_RULES.maxRunMs`），到时服务端自动结束（`timeout`）；断线或刷新在 30 分钟内可从当前 step 继续。
- 无输入：**30 秒**（`SCENE_RULES.idleLoopMs`）回到待机循环，**60 秒**（`SCENE_RULES.idlePromptMs`）她问「还在吗」，**5 分钟**（`SCENE_RULES.idleEndMs`）自动结束（`idle`），不扣任何东西。
- 奖励（亲密度、回忆卡、约定）只由服务端发放；同一场景**每个 JST 日只有第一次运行**发奖（`SCENE_RULES.rewardedRunsPerDay`），重玩照常播放但不发奖（防止刷免费抽）。场景算作一次相处（计入相处天数），场景里进入新阶段同样送 1 次免费单抽。
- 场景内自由对话（`input.mode = free`）走普通聊天链路：计入每日条数、写入聊天记录与长期记忆；被拦截时不计数、场景不前进。
- 数值在 `packages/shared/src/rules.ts` 的 `SCENE_RULES`。
- 五幕的小游戏见 §13.5；语音分钟、延长与她的实时语音（#74 #73）见 §13.6。

### 13.2 场景怎么开始（#65）

- 三种来源，写入 `scene.trigger(source)`，指标页显示占比（目标 40 / 30 / 30，`TRIGGER_SOURCE_TARGET`，`packages/shared/src/contracts.ts`）：
  - **request**：他在聊天里要求（persona 服务每轮并行读取 `{ intent: scene:<id> | none, mood }`，与安全分类同一次调用；没有可提供的场景时意图恒为 none）。条件满足 → 她答应，场景在她那句话之后打开；不满足（阶段 / 没有那张卡 / 时段 / 天气 / 点数 / 他语气太冲）→ 她用人设撒娇、讨价还价或拒绝，不出系统提示，可以反提议另一个可开始的场景（按钮，不强制）。他在房间里直接点场景入口也算 request。
  - **proposed**：进入她的房间（陪伴首页 = 她的待机场景）或在房间里安静 **90 秒**（`TRIGGER_RULES.idleProposeMs`）时，按概率 **0.3**（`TRIGGER_RULES.proposeRate`）从可用场景里挑一个提议：约定 > 没看过的变体场景 > 天气限定 > 招牌 > 其他。提议是一句话 + 「うん、しよう / また今度」。
  - **time**：此刻正合适的场景（脚本限定了天气、她的作息、单一时段，或刚达到的阶段）先于她的提议、不掷骰子；收件箱里写了 `payload.sceneId` 的事件（叫醒、晚安、约定到期、初雪、生日）打开时同样按 time 提供。
- 限流（`TRIGGER_RULES`，全部**待确认**）：她的提议每人每 JST 日最多 **5** 次（`maxProposalsPerDay`）、两次之间至少 **1 分钟**（`minProposalGapMs`）；他说「また今度」的场景 **6 小时**（`declineCooldownMs`）内不再提；time 类每日最多 **3** 次（`maxTimeOffersPerDay`）、同一场景一天一次；提议 **10 分钟**（`offerTtlMs`）不回应即失效（之后再点仍能开始，但记为 request）；他正在场景里、或今天已经玩过（发过奖）的场景不提。
- 只提供能玩的场景（发布规则，§9.4）：正式环境只提供已审校且片段齐全的场景；demo 场景只在 demo / 原型模式；网页端缺少任一片段的提议不显示。
- 场景内自由对话可以按脚本声明的 `jumps` 转向（`directive.jumpTo`），脚本没声明的目标一律忽略。

### 13.3 系统场景包（#71）

五位共用的小场景，由台词拼成（`packages/shared/src/scenes/system.ts`），只用现有素材：她在房间（`<star>-hero`）、近景（`<star>-breath`）、熄灯后的夜景（`<star>-night`）。尺度同 §7：最多到耳边低语，温柔、不涉性。

- **晚安**：他本地时间 22:00–05:00（`SYSTEM_SCENE_RULES.goodnightHours`，`users.tz`，未知 = JST）进房间时作为 time 提供；在聊天里说「おやすみ」也会开始（意图识别的 `cue`，只在这段时间列出）。月卡（`ACCESS.nightWhisper = 'pass'`，v1.1 月卡只能靠幸运码）= 近景耳语，五句轮换、一夜一句（午夜后仍是同一夜那句），「もう少しだけ」再多一句；非月卡 = 她的普通晚安一句。最后熄灯。
- **初雪 / 台风（大雨、强风预警）/ 雨夜**：天气消息（§12.2，`weather.events`）的 `payload.sceneId` 指向对应场景；收到后 24 小时内（`SYSTEM_SCENE_RULES.weatherSceneMs`）打开消息或进房间都会提供。她把该事件的三句台词依次说完（消息里那句是其中之一），中间他回一句；初雪有回忆卡「ふたりの初雪」。雨夜只在傍晚与夜里。
- **她的生日 / 他的生日**（§11.5）：她的生日只在事务所确认后（测试站例外），他的生日按他的时区；当天进房间必定先提供一次（time 优先于其他），生日消息也带 `sceneId`。全景 → 礼物（她的生日由他选礼物，不倒计时）→ 近景感谢 / 祝福 → 回忆卡。
- **约定兑现开场**（§11.4）：`kind = scene` 且没有指定场景的约定，在兑现窗口内（或刚被问候 / 收件箱兑现后一个窗口内）进房间提供；到期消息带 `sceneId = promise-kept-<star>`。回忆卡就是约定本身那张，不另发。
- 优先顺序：约定 > 他的生日 > 她的生日 > 初雪 > 台风 > 雨夜 > 晚安；受 §13.2 的 time 限流（每日 3 次、同一场景一天一次、「また今度」6 小时）约束；她的随机提议不会挑系统场景。
- 奖励（`SYSTEM_SCENE_RULES.affinity`，待确认）：晚安 +2、耳语 +3、天气 +3、生日 +10、约定 +5；每个 JST 日第一次运行发奖，同 §13.1。

### 13.4 语音输入（#72）

- 聊天与场景里按住麦克风说话、松开发送；短按 = 开关。说完静音 1.2 秒自动停、最长 30 秒、8 秒没声音放弃（`VOICE_INPUT.silenceMs` / `maxMs` / `noSpeechMs`，`packages/shared/src/voice.ts`）。一按下就停掉她的语音和当前台词，轮到他。
- 识别出的文字走与打字完全相同的聊天 / 场景链路，所以计次与记忆只有一份；文字输入随时可用，麦克风被拒时焦点回到文字框。
- 浏览器有自带识别（Chrome、Edge、Safari）就用它，边说边出字；没有（Firefox 等）或 iOS 关了听写时，录一段交给 `POST /v1/asr`（需登录，≤ 1 MB `VOICE_INPUT.maxBytes`），由 Workers AI Whisper 转写；音频只在内存里处理，不落库、不写日志，识别失败不扣次数。两者都没有就只留文字。
- 例外：告白回答处他勾选保留录音时，改用录音识别，以便保存（`docs/compliance-jp.md` §7.3）。
- **免提模式（可选，#72）**：麦克风旁的「耳朵」开关（默认关，只记在本机）。打开后，她说完、在等他开口时（场景里的输入步、聊天页她的回复结束后），浏览器读取麦克风音量（简版 VAD：音量超过阈值持续 0.2 秒，`VAD.loud`）即自动开始识别，静音后照常自动发送；等待期间不录音、不上传，只在浏览器里看音量。她说话、他在打字、有东西还在路上时不侦听。被环境声误触发时不提示「没听到」，继续等待。麦克风被拒绝时自动关掉并提示。

- **她的实时语音（#73）**：她自由对话的回复与 `tts: true` 的台词（带他的称呼）实时合成，脚本台词仍用预生成语音。网页按句切分，逐句请求 `POST /v1/tts` 并排队播放（播放当前句时预取下一句，先播首句），字幕随每句开始显示；他一开口（#72）立即停止。服务商经 Worker 中转（`tts.internal`，密钥为 Worker secret），默认 `none`；现用 Fish Audio S2.1-Pro（`fish`，负责人 2026-10-02 选定）；阿里云百炼国际站 Qwen3-TTS-VC（`qwen`）与 BytePlus Seed Speech 声音复刻 2.0（`byteplus`）也已实现，可按艺人分别指定（`TTS_VOICES`，接口、试听结果与选型见 docs/tts.md，`npm run voice:enroll` / `voice:pilot`）；只有某位艺人有克隆音色且对应密钥已配置时才开启（`/v1/config` 的 `voice` / `voiceStars`），Fish Audio / MiniMax / ElevenLabs 仍是空位。她的房间：她的回复完整到达后逐句合成播放，与场景共用她的一条语音通道（N-32）；声音开着时，说话片段只在音频真正发声时播放（`playing` 事件后约 80 ms 起，句间停顿与结束时回到待机，约 140 ms 交叉淡化），字幕按每句音频时长逐字出现，下一句在本句播放时预取；声音关闭或失败时字幕按原速度打字；目錄里的「聲音」是开关（本机记住，默认开），只有开着时输入框旁才显示「聲音 剩N分」；场景台词仍用预生成语音。负责人 2026-10-02 决定对**所有登录会员**开放（`VOICE_RULES.ttsRoles`）。没有她的克隆音色时（`TTS_VOICES` 里没有她）一律字幕，**绝不用通用合成音（例如 Workers AI MeloTTS）代替她的声音**。关闭、断网、用完分钟或服务商失败都退回字幕，不报错。每句的请求 id 在调用服务商之前先记账（合成成功后写入秒数、失败则撤回），同一 id 只合成一次，重复提交 409，前端按字幕处理。
- **已知限制（v1.1）**：他在场景里的语音输入秒数（`voiceMs`）由网页上报，服务端不核对，是君子协定：少报或不报只会让他多用一点语音时间（不涉及点数或真实费用）；多报只会扣他自己的。上限由接口保证：每一步最多 30 秒（`VOICE_INPUT.maxMs`，超出 400），同一步（`runId`+`seq`）只计一次。以后若要严格计量，改为由服务端按 `POST /v1/asr` 收到的录音时长记账。
- **只说她自己的话**（已实现）：`POST /v1/tts` 不接受任意文本。服务端给她的每句可实时合成的台词签名（她的聊天回复 `voiceSig`、场景里 tts / 自由对话 / 带称呼的台词 `voiceSigs`，HMAC 绑定账号、艺人与原文），请求带原文、签名与句序号；签名不符（他的话、改过的句子、别人的或别的艺人的）一律 403 `not_her_line`；`{name}` 由服务端用她对他的称呼填入，其他占位符不合成；按与网页相同的 `splitSentences` 切句后只合成那一句。限流：每 IP 每分钟 60 次、每账号每分钟 40 句（429）；每句按秒计入语音分钟。待验收：相似度、首包延迟（< 800 ms，试听 p50 327 ms）、字幕同步误差（< 300 ms）（#73）。

- **四层场景**（`packages/shared/src/scenes/<star>/variant-<star>-<层>.json`，共 20 个，id 即 catalog 预留的 `variant-<star>-{1,3,6,10}`）：1 层 お披露目（空房间 → 她穿着新衣服入画，问他觉得怎样）；3 层 ふたりの時間（まひろ 聊今天、奈々 跳一小段、うんぱい 猜拳抢手柄、アリス 茶与八音盒、えいみ 一题大喜利）；6 层 近くで（近景、耳边的话、えいみ 是香水；他要求更近时她在人设里拒绝）；10 层 腕のなかで（拥抱，之后她在主页穿着这身等他）。尺度：性感不露骨，最高到近景、耳边说话、拥抱，越线由她本人拒绝。结束各 +30 变体 xp（`VARIANT_RULES.sceneEndXp`），1 层与 10 层各得一张回忆卡。

### 14.2 Pickup（#78）

- Pickup = 某位艺人的普通卡池（她的 30 张）在一个期间内把她的变体卡提到 SSR 以上出货的 **50%**（`PICKUP_RULES.share`，**待确认**）；其余 SSR 以上的卡按原比例分剩下的部分。SSR 以上的合计概率（5%）、天井（80 抽）、N〜SR 概率都不变；以现在的暂定选卡（UR），该卡从 0.5% 升到 2.5%，她的 4 张 SSR 各从 1.125% 降到 0.625%。其他卡池一律不变。
- 期间由管理后台排期（`/v1/admin/pickups`，最长 `PICKUP_RULES.maxDays` = 31 天，**待确认**），排期后即在提供割合页公告；比例在创建时写入 Pickup，之后改规则不影响已公告的 Pickup。
- 聊天引导：他问起她的变体服装（意图 `outfit:<cardId>`）→ 已拥有：有可进入的变体场景就开始（#76），否则她只是高兴；未拥有：她在人设里说「その服、まだ持ってないの…」，若有进行中的 Pickup，台词下出现一个小链接（不弹窗、不倒计时）。她也会偶尔主动提起：概率 0.2、同一用户 3 天内最多一次、每个 Pickup 最多 2 次（`PICKUP_RULES.invite.rate` / `gapMs` / `perPickup`，**待确认**），只在 Pickup 进行中且他没有这张卡、他情绪不低落时；邀约台词已审校（#84，§9.4）。
- 链接出现写 `variant.prompted`（`via: ask | invite`），Pickup 中抽到变体卡写 `variant.drawn`（`pickup: true`）。
- 合规：`docs/compliance-jp.md` §3.1。
- 数值在 `packages/shared/src/rules.ts` 的 `VARIANT_RULES`、`VARIANT_CARDS` 与 `PICKUP_RULES`。

### 14.3 礼物与偏好（#77）

- 目录（`packages/shared/src/gifts.ts`）：20 种固定的数字礼物，五位共用——通用 5 种（花束、马卡龙、香薰蜡烛、小熊、闹钟）+ 来自五位人设 `likes` 的 15 种。三语名称，价格 **50–300 pt**（`GIFT_RULES.prices`，**待确认**）。无实体、无随机礼盒、不可转让或换现。
- 她的偏好（`packages/shared/src/tastes.ts`，**暂定**，随人设终稿 #84 调整）：每位 3–4 种喜欢、0–1 种不喜欢（例：まひろ 喜欢メロンパン / ココア / 猫，不喜欢目覚まし時計）。偏好只在服务端读取；网页入口包里没有，界面不显示「她喜欢什么」，只显示「他已经知道的」。
- 送礼 `POST /v1/gift { star, giftId, cardId?, lang? }`：扣点数、写礼物行、加亲密度 xp（以及穿着变体卡时的变体 xp）是**同一个原子步骤**；点数不足 402 `insufficient_points`，超过每日上限 409 `gift_limit`，都不写任何东西。写 events `gift.sent`。
- 数值（全部**待确认**，`GIFT_RULES`）：每人每 JST 日最多 **5** 次（`perDay`，五位合计）；xp = 价格 × 0.2（`xpPerPoint`），偏好礼物 **×2**（`taste.liked`，验收：正好是普通礼物的 2 倍），不喜欢的 ×0.5（`taste.disliked`，仍 ≥ 1）。
- 关系阶段：礼物只加 xp，**不算相处天数**；天数已满足时可以因礼物 xp 进入下一阶段（同样发 1 次免费单抽），天数不够时再多礼物也跳不过（§10.1）。
- 变体卡（§14.1）：带 `cardId`（她的、他拥有的变体卡）时，礼物 xp 另外 ×1–3 加到该卡的变体好感（普通 / 不喜欢 ×1，偏好 ×2，她提过的偏好 ×3，`GIFT_RULES.variantMultiplier`，在 `VARIANT_RULES.giftMultiplier` 范围内）；主亲密度只加一次礼物 xp，不再叠加变体联动的 50%。网页端「穿着她」的状态由 #76 提供，届时传 `cardId`。
- 她的反应：人设服务 `POST /v1/gift` 用她的完整人设写 1–2 句，知道礼物合不合她的口味；如果是她提过的，会引用她当时说的那句话。模型不可用、超时或输出被拦截时，用预写的反应（每位 × 偏好 / 普通 / 不喜欢 / 她提过的 × 三语）。反应写进她的聊天记录。
- 偏好藏在日常对话里：他第 5 条消息及之后每 20 条（`GIFT_RULES.hintAtTurn` / `hintEveryTurns`），提示词允许她**自然地、顺口**提一句最近想要的东西（他还不知道的那种，轮流），绝不开口要礼物、不提点数或花钱；被安全层引导的回合不提。她的回复里说出自己喜欢的东西、或他送了她喜欢的礼物 → 记入聊天记忆 facts `her_wishes`（只由 API 写，人设的记忆模型改不了）。礼物面板显示「♥ {她}の好きなもの：…」并在对应礼物上加标记。
- 界面：她的聊天页顶栏与陪伴首页的「プレゼント」按钮打开礼物面板（390×844 内），显示所持点数、今日剩余次数、「数字物品、不寄实物、点数不可退款或换现」说明。
- 退会时删除该用户的全部礼物记录（聊天记忆本来就删除）。合规见 `docs/compliance-jp.md` §4。

## 16. 指标（#52）

- 事件只由服务端写入（D1 `events`，`app.recordEvent`），不由浏览器上报；`props` 只放 id 与枚举（`EVENT_PROPS`，`packages/shared/src/contracts.ts`），不含聊天文本；保留 180 天（`EVENT_RETENTION_DAYS`），按 JST 日删除；退会后 `user_id` 置空，次数仍计入。
- 事件：`stage.changed` `confession.reached` `confession.answered` `call_name.answered` `alarm.set` `wakeup.opened` `promise.due` `promise.kept` `room.entered` `scene.trigger` `scene.start` `scene.end` `variant.prompted` `variant.drawn` `variant.scene_opened` `gift.sent`。
- 管理后台「指標」页（`GET /v1/admin/metrics?grain=day|week&days=1–180`）按 JST 天或周（周一起）给出原始计数，定义见 `MetricsCounts`：
  - **告白到达率** = 当期新用户（cohort）中有 `confession.reached` 的比例；
  - **叫醒闹钟设置率** = 当期活跃用户（当期有任何事件的用户，新老都算）中，到当期最后一天为止有过 `alarm.set` 的比例（#57：设过闹钟的用户 / 活跃用户）；
  - **约定兑现回访率** = 当期到期的约定（`promise.due`）中按 `promiseId` 配对到 `promise.kept` 的比例；
  - **每次进房间的场景触发** = `scene.trigger` ÷ `room.entered`，另显示触发来源占比与目标 40 / 30 / 30（`TRIGGER_SOURCE_TARGET`）；
  - **变体卡转化** = 被引导（`variant.prompted`）→ 同期抽到（`variant.drawn`）→ 抽到当天打开换装场景（`variant.scene_opened`）；
  - **7 日留存差**：前 7 天（第 0–6 天）触发过场景的用户与只聊天的用户，第 7–13 天回来的比例之差。
