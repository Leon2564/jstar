# 日本合规要点（需律师最终确认）

本文件是工程实现对应的合规约束，不是法律意见。最后更新：2026-09-26（v1.1 基线，#53）。

- §1–§6：卡牌、概率、点数、AI 身份、年龄与尺度。
- §7：个人信息（APPI），v1.1 的每一项新数据各占一小节。

## 1. 随机只发生在一侧

- **线下**：实体盲盒是商品本体，随机性在拆包时发生。
- **线上**：付费抽卡的产出只能是数字内容，**不得**抽中后寄送实物。线上付费抽实物属于「オンラインオリパ」，2026 年 9 月已有律所就此向消费者庁申请调查。
- 代码层面：`/v1/gacha/draw` 的产出只有 `cardId`；发货相关字段不存在。

## 2. カード合わせ（集齐换奖）禁止

付费抽到的卡「集齐一套换奖品」在《景品表示法》下被禁止。集齐只能给图鉴荣誉，或由免费、确定性购买渠道发放。
- 代码层面：卡池与奖励配置里没有「集合条件 → 奖品」的字段，新增前必须先过法务。
- 变体卡（#75）：好感、心意与场景都按**单张卡**计算，没有「持有几张变体卡 → 奖励」；提供割合页的变体说明不含集齐奖励字样（`apps/web/tests/unit/rates.test.tsx`）。

## 3. 概率公示

抽卡概率在界面上公示（`gacha.ratesBody`），修改概率需要公告。
- 代码层面：概率只在 `packages/shared/src/rules.ts`（`RULES.rates`）里定义，改动走 PR（没有在线修改概率的接口）；提供割合页（`GET /v1/gacha/rates`）与抽卡读同一份配置；Pickup 的排期与修改写审计日志（§3.1）；每次抽卡保存种子，纠纷可复现。

### 3.1 Pickup（概率提升，#78）与景品表示法

某张变体卡在一个限定期间的卡池里概率提升（Pickup）。概率提升的表示属于「表示」，按景品表示法的有利誤認表示（第5条第2号）处理：让用户以为比实际更有利，就是违法表示。因此：
- **写数字，不只写「UP」**：卡池页与提供割合页都写出该卡在 Pickup 中的概率、它在普通卡池里的概率（「2.5%（通常 0.5%）」）、它占 SSR 以上的比例，以及含天井的实际出现率；同一档其他卡因此下降多少，表里逐档逐张写明。
- **数字从配置算出**：公示与抽卡用同一份配置、同一个函数（`pickupDisclosure` / `drawPickupPulls`，`packages/shared/src/gacha.ts`），各档之和恰为 1；服务端抽样 10 万次与公示一致（`packages/shared/tests/pickup.test.ts`、`apps/api/tests/pickup.test.ts`）。
- **只动这一个池**：SSR 以上的合计概率、天井、N〜SR 的概率与她的普通卡池相同；「全員」与各人的普通卡池概率、同一种子的抽卡结果都不变（改动前的指纹测试）。
- **期间明示，事前公告**：Pickup 有起止时间（JST，显示到分钟），一经排期就出现在提供割合页（「開催予定」），开始前即公告；期间内概率不变——比例在创建时写入 Pickup，之后改 `rules.ts` 也不影响已公告的 Pickup 与已抽结果的复现。排期与修改写审计日志（`pickup.create` / `pickup.update`）。
- **不制造紧迫感**：不弹窗、不倒计时、不写「今だけ」「残りわずか」；聊天里只在她的台词下出现一个小链接。她主动提起有频率上限（`PICKUP_RULES.invite`，待确认），他情绪低落、疲惫或语气冲时不提，台词不提抽卡、点数、价格、期限（`apps/agent/app/intent.py` `NOT_A_SALE`）。她的邀约台词中带「今だけ / 今月」的第 3 句不用于此。
- **不设集齐奖励**（§2 不变），碎片兑换仍可直接换变体卡（免费、确定性的渠道）。
- 比例（`PICKUP_RULES.share`，现为 50%）与邀约频率是负责人的决定（#84 待确认）；Pickup 的表示方式需日本律师最终确认（#84 法务）。
- 代码层面：`apps/api/src/lib/pickup.ts`、`apps/api/src/modules/gacha.ts`（`/v1/gacha/rates` 的 `pickups`、Pickup 抽卡仅在期间内）、`apps/api/src/modules/admin.ts`（`/v1/admin/pickups`）、`apps/web/src/pages/legal.tsx`（提供割合）。无新表：Pickup 以 JSON 存在 `pools` 表（id `pickup:…`）。

## 4. 点数属于前払式支払手段

未使用余额在基准日超过 1000 万日元需向主管部门备案；有效期与不退款要在「资金決済法に基づく表示」中写明。
- 代码层面：v1.0 / v1.1 不开售（`RULES.shopOpen = false`），`/v1/shop/*` 一律 404 `shop_closed`；开放时在正式环境只能走支付商流程（非演示模式 501 `use_checkout_flow`）。
- 礼物（#77）：点数的一种使用方式，换的是固定的数字物品（价格固定、没有随机礼盒、不寄实物、不可转让、不可换现），不改变点数作为前払式支払手段的性质；礼物面板写明「数字物品、不寄实物、已使用点数不可退款或换现」。礼物不与抽卡挂钩（不送抽卡、不改概率），也没有「送齐 N 种 → 奖励」（§2）。偏好加成只影响亲密度 xp，且受关系阶段最少天数限制，不是可购买的奖品。登录、签到得到的免费点数与购买的点数同样可用于礼物；将来开放付费时，「資金決済法に基づく表示」需把礼物列为用途之一（#84 法务确认）。人设不得主动索要礼物或提及点数（提示词规则 + `apps/agent/tests/test_gifts.py`）。

## 5. AI 身份必须明示

与用户对话的是「本人公认的 AI」，界面固定展示，且用户询问「是不是真人」时，人设必须直接说明自己是 AI。
- 代码层面：`apps/agent/app/safety.py` 的 `AUTHENTICITY` 分类强制返回 disclosure 话术，有测试覆盖。

## 6. 年龄与内容尺度

- 全站年龄确认，注册时再次确认生年月日。
- 内容停在「性感不露骨」：露骨请求由人设婉拒，未成年相关请求硬拦截。
- 未满 18 岁关闭账号后的再注册冷却（v1.1.1 M7）：生日确认未满 `RULES.minAge` 时账号当场匿名化关闭（同退会），同一邮箱 `RULES.underageCooldownDays`（30）天内不能再注册（`403 signup_cooldown`）。只保存 `HMAC-SHA256(服务器密钥, 邮箱)` 与截止时间（`signup_blocks`，`apps/api/migrations/0030_signup_blocks.sql`），不保存邮箱本身，表本身无法还原地址；冷却期过后该行不再起作用。测试：`apps/api/tests/api.test.ts`。隐私政策需补一句「年齢確認で利用できない場合、再登録防止のためメールアドレスを不可逆に変換した値を30日間保存」——文案待法务确认（#84）。
- AI 生成的性感内容是否落入 AV 新法的程序要求，**必须由日本律师确认**，这是唯一尚未有定论的一项。
- 五幕的小游戏（#66–#70）：他的回答先过与聊天相同的内容边界；越线的弹幕她不会读出（换成不含原文的婉拒模板），大喜利的点评过与「她的消息」相同的出站检查，不合格就不说。猜拳由服务端随机、不花钱，三条分支奖励相同，输赢只决定剧情，不构成付费随机（§1）。

## 7. 个人信息（APPI）

v1.1 新增的每一项个人数据都按「最小化、目的限定、可删除」处理：只存功能必需的、只用于写明的目的、本人可以删除、退会时一并删除（`users.anonymise`）。隐私政策对应的段落在各小节注明。

### 7.1 位置情報（用户自选城市，#62）

用户所在城市属于个人信息（APPI），按「最小化、目的限定、可删除」处理。
- 只到城市级别：用户从搜索结果里选择城市，服务端按地点 id 重新查询后只保存地名与经纬度取整到 0.1°（约 10 km），不保存地址，不读取浏览器定位（`permissions-policy: geolocation=()` 保持关闭）。
- 目的限定：只用于该城市的天气（显示与对话上下文），不做地理围栏、不用于推荐或广告。
- 对话上下文（#63）：城市名与该城市的天气随聊天请求交给 persona 服务、进入模型提示词（与聊天内容同一通道、同一模型供应商），只用于她对比两地天气；不写入记忆、事件或日志。她自己的城市在出生地未经事务所确认前不出现在提示词里。
- 第三方提供：城市搜索词与天气坐标发送给 OpenMeteo GmbH（瑞士），不附带账号、邮箱或 IP（经 Worker 中转）。隐私政策「あなたの街（任意）」一节已写明。
- 删除：用户可随时清除；注销时与账号一起删除（`users.anonymise`）；天气表按 0.1° 方格存储、不关联用户，无人再选的方格由下一次 tick 删除。
- 代码层面：`apps/api/src/modules/world.ts`、`user_cities` 表（`apps/api/migrations/0011_weather.sql`），测试 `apps/api/tests/weather.test.ts`。
- 数据许可：Open-Meteo 数据为 CC BY 4.0，使用处须标注来源；免费档仅限非商业用途，正式商用需改用其付费档（#84）。

### 7.2 叫醒闹钟（#57）

叫醒时刻、星期与时区反映用户的生活作息，同样按 APPI「最小化、目的限定、可删除」处理。
- 只存设定本身：时刻、星期、由谁叫醒、开关，以及浏览器上报的 IANA 时区（`users.tz` 与 `alarms.tz`）；不存位置，不从时区推断所在地。
- 目的限定：只用于按用户的时间送出叫醒（推送与 11:00 前的叫醒画面）；指标只记 `alarm.set` / `wakeup.opened` 与艺人 id，不含时刻。
- 推送正文只有她的一句叫醒话（#50 的验收标准），不含用户设定的时刻或任何个人信息。
- 删除：关闭时保留设定（便于再开）；注销时与账号一起删除（`users.anonymise`）。隐私政策「目覚まし（任意）」一节已写明。
- 代码层面：`apps/api/src/modules/alarm.ts`、`alarms` 表（`apps/api/migrations/0014_alarms.sql`），测试 `apps/api/tests/alarm.test.ts`。

### 7.3 告白的录音（#55）

他回答告白时的声音是个人信息（APPI；声音可识别本人）。按「明示同意、最小化、目的限定、可删除」处理。
- **明示同意**：告白回答处有一个默认关闭的勾选框「この答えの声を、思い出として残す」，旁边写明只有本人可以回放、随时可删除、退会时删除。未勾选时不保存任何录音：识别用的片段照 #72 在内存中处理后丢弃。勾选后改用录音识别（MediaRecorder → `/v1/asr`），以便有一段可保存的录音；该浏览器不能录音时不显示勾选框，只保存文字。
- **只在「是」之后保存**：录音在他回答时只留在该页面内存；只有判定为 accept 且已勾选时才上传（`PUT /v1/confession/memories/:id/audio?consent=yes`），服务端记录同意时间 `consented_at`。not yet / decline 的录音一律丢弃。文字（他的回答）作为回忆的一部分保存，与聊天记录同等对待。
- **目的限定**：只用于他本人在「思い出」页回放。不用于训练、不给艺人或运营查看、不进事件表（`confession.answered` 只有 star 与 answer）、不写日志。
- **访问**：只有本人的会话能读取（`cache-control: private, no-store`），前端以 blob URL 播放，没有公开链接；唯一的例外是他本人导出文件里的签名链接（§7.6，24 小时后失效）。
- **删除**：可在「思い出」页单独删除录音（文字保留）；退会时 `confessions` 与 `confession_voice` 全部删除（`users.anonymise`），回忆存储里该用户前缀下的文件一并删除（§7.6）。
- **存储**：大小上限 `CONFESSION_RULES.voiceMaxBytes`（768 KB）。#51 起存进回忆存储（R2 私有桶 `MEMORY`，key 以 `user_id/` 为前缀，§7.6）；未绑定桶时仍照 #55 以 base64 存在 D1 的 `confession_voice` 行内，桶绑定后旧录音在下一次读取或 tick 时自动迁入。
- 代码层面：`apps/api/src/modules/confession.ts`、`apps/api/migrations/0018_confession.sql`、`apps/web/src/scene/player.tsx`（勾选框）、`apps/web/src/components/confessionMemories.tsx`，测试 `apps/api/tests/confession.test.ts`。隐私政策需补一句「告白の録音（任意）」——文案待法务确认（#84）。

### 7.4 呼び方与「她会被你改变」（#56）

他设定的「呼び方」可能是真名，夸奖计数反映他的偏好，按 APPI「最小化、目的限定、可删除」处理。
- **只存必要的**：「呼び方」是他主动输入的一个名字（20 字内，服务端拒绝邮箱、链接、电话号码样式）；夸奖只存「样子 id + 次数 + 最后时间」，不存他的原话。
- **目的限定**：名字只用于她称呼他（进入提示词，与聊天内容同一通道、同一模型供应商）；计数只用于提示词与房间待机视频的选择。事件表只有 `call_name.answered` 的 star / to / answer，不含名字。
- **安全**：名字在 persona 服务里过与聊天相同的安全过滤，不通过就不使用（她改用默认称呼）。
- **他喜欢的相处方式**（`favorite_ways`）：只存最多 5 个由记忆模型归纳的短标签（「寝る前のおしゃべり」），不存他的原话；像引用的（引号、句末标点、第一人称、与他的消息逐字相同的长句）、含联系方式或露骨内容的一律丢弃（`apps/agent/app/memory.py` `clean_ways`）。只用于她的提示词，与其他记忆 facts 同存于 `chat_memory`，注销时一并删除。
- **删除**：「我的」里可随时改回账号名；注销时 `call_names`、`look_praise`、`call_name_prefs` 全部删除（`users.anonymise`）。
- 代码层面：`apps/api/src/modules/bond.ts`、`apps/api/migrations/0021_call_names.sql`，测试 `apps/api/tests/bond.test.ts`。隐私政策需补一句「呼び方（任意）」——文案待法务确认（#84）。

### 7.5 他的生日（#61）

注册时确认 18+ 用的生年月日（`users.birthday`）是个人信息（APPI）。#61 把它的**月日**另用于「生日当天她的祝福」，按「最小化、目的限定」处理：
- **只读月日**：日历（`packages/shared/src/calendar.ts` `birthMonthDay`）只取 MM-DD；年份只用于 18+ 确认，不进入任何事件、提示词、消息、推送或接口响应（`GET /v1/calendar` 只返回事件种类）。她不知道他的年龄，提示词明确禁止提及或猜测。
- **锁屏不暴露**：生日那条消息的推送正文是中性的一句（`HIS_BIRTHDAY_PUSH`），祝福只在应用内显示。
- **不进事件表**：`calendar.greet` 不写 product event（事件表保留 180 天、管理员可读，事件日期会暴露生日）。
- **可停止**：「彼女からのメッセージ」设为「受け取らない」时不发任何节点消息。
- 隐私政策「お誕生日」一节已写明用途（文案待法务确认，#84）；退会时生年月日照旧删除（`users.anonymise`）。
- 艺人的生日是真实人物的信息：只有事务所确认（#84）后才出现（`world.ts` `confirmed`）；测试站（演示模式）例外。
- 代码层面：`apps/api/src/jobs/calendarGreetings.ts`、`apps/api/src/lib/calendar.ts`、`apps/api/src/modules/calendar.ts`，测试 `packages/shared/tests/calendar.test.ts`、`apps/api/tests/calendar.test.ts`。

### 7.6 回忆资产：存储、导出、保留与停服保全（#51）

回忆卡、告白的回答与录音、约定、聊天记录是用户最核心的资产，也是个人信息（APPI）。按「安全保存、本人可取回、离开即删除」处理。
- **存储**：文件（告白录音，将来的场景截图）存在 R2 私有桶 `MEMORY`（测试站 `jstar-test-memory`，正式 `jstar-memory`），key 一律以 `<user_id>/` 开头。API 容器没有外网，只能经 Worker 的 `memory.internal` 中转（带内部密钥，只能按 key 存 / 取 / 删，或删除某一用户前缀下的全部文件；不能列举），桶本身没有公开访问。未绑定桶时录音照 #55 以 base64 存在 D1。文字类资产（回忆卡、约定、聊天）在 D1。
- **回忆卡的类型**：`memories.kind` 为 chat / scene / confession / promise，`scene_id` 记录生成它的场景，`still` 预留给场景截图（#80 之后）；迁移 `0025` 把可精确识别的旧卡标为对应类型，其余为 chat。
- **导出（本人开示）**：「思い出」页的「思い出を書き出す」→ `GET /v1/me/export`，一个 JSON 文件：账号（id、昵称、邮箱、语言、注册时间）、全部回忆卡（与页面同一列表）、告白的回答与录音链接、全部约定、聊天记录。录音不直接放进文件，而是签名链接：不需要登录即可下载，`MEMORY_RULES.linkTtlMs`（24 小时，**待确认**）后失效；录音被删除或退会后链接立即失效。每个 JST 日 1 次（第二次 429），导出记录一周后删除；每次导出写审计 `memories.export`（只记条数）。
- **删除**：单独删除录音时先删文件再清行；退会（`users.anonymise`）在同一事务里删除 D1 的全部行，并写入待删队列 `memory_purges`；随后立即删除 R2 中 `<user_id>/` 下的全部对象，失败的由 tick 任务 `memories.assets` 每小时重试，直到对象数为 0。
- **保留期（待确认，#84 法务）**：`MEMORY_RULES.retentionDays`，默认 `null` = 不按时间删除（录音保留到本人删除或退会）。设定后，tick 任务删除同意保存超过该天数的录音（回忆卡与文字保留）。
